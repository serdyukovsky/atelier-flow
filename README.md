# Atelier Flow v1.2.3

Личный шаблон рабочего процесса для разработки продуктов с ИИ-агентами. Он помогает вести сайт или приложение от брифа до проверки, но не является готовым сайтом, фреймворком или набором автоматически запускаемых агентов.

Основной сценарий — делать качественные публичные сайты: сначала понять задачу и визуальное направление, затем реализовать, проверить в браузере, учесть базовые SEO, доступность и безопасность.

## Что даёт шаблон

- не нужно каждый раз заново объяснять агенту, как работать с проектом;
- агент сам создаёт и ведёт проектный контекст — пользователь не заполняет формы;
- для сайта задана последовательность: контент и структура → SEO-цель → визуальное направление → дизайн-система → реализация → ревью;
- используются только активные профиль и workflow, а не все файлы шаблона сразу;
- `workflow-log.md` показывает, что действительно было использовано и проверено;
- `VERIFICATION.md` фиксирует реальные команды lint, typecheck, tests и build, а агент запускает их пропорционально риску изменения, а не после каждого сообщения.
- новая визуальная система сначала проходит visual gate: один экран, desktop/mobile скриншоты, независимая критика и только затем масштабирование на весь сайт.

## Быстрый старт

1. Открой Atelier Flow в Codex или Claude Code и попроси создать проект. Агент обязан создать отдельную соседнюю папку, а не строить сайт внутри репозитория шаблона.
2. Или создай скелет одной командой:

   ```bash
   ./scripts/new-project.sh ../my-project
   ```

3. Открой созданную папку проекта в Codex или Claude Code.
4. Напиши агенту обычным языком, что нужно сделать. Ничего вручную заполнять не нужно.

Пример первого сообщения для нового сайта:

```text
Нужно сделать сайт для [продукт / аудитория / задача].
Используй website-профиль и workflow new-site.
Хочу современный, выразительный digital-интерфейс, а не шаблонный AI-дизайн.
Paper-стиль запрещён: без бежевых/кремовых бумажных поверхностей,
зерна, faux-editorial и handmade-эстетики.
Референсы: [ссылки или описание].
Сначала разберись в задаче, предложи визуальные направления и стек;
задавай только вопросы, которые действительно меняют результат.
```

Агент должен сам создать или обновить `PROJECT.md`, выбрать минимальный подходящий workflow, определить стек и проверить доступные возможности. Значимый выбор — например, CMS, база данных или смена фреймворка — он выносит на согласование.

## Какой режим выбрать

| Задача | Что написать агенту |
|---|---|
| Небольшая правка | «Используй quick-task» |
| Новая страница или обычная функция | «Используй standard-feature» или `website-page` |
| Новый сайт или крупный редизайн | «Используй new-site» |
| Проверка перед публикацией | «Запусти pre-release-review» |

Если не назвать workflow, агент обязан выбрать его сам: `quick`, `standard` или `complex`.

Для обычной итерации агент сначала называет короткий scope проверки. Например: «локальная CSS-правка — проверяю изменённый маршрут; typecheck, build и полный browser QA не нужны». Полный набор проверок запускается для релиза, существенного редизайна или рискованного изменения.

## Рекомендуемый старт для сайта

Для первого сайта не включай всё подряд. Начни с:

```text
Profile: website
Stack preset: website-next
Workflows: new-site → website-page → browser-qa → visual-review → pre-release-review
Modules: basic SEO + security baseline
```

`Payload`, расширенный SEO-набор, backend API, Telegram/Max mini apps и другие профили остаются выключенными, пока проекту они не нужны. Их присутствие в папке не означает, что агент обязан их читать или использовать.

## Skills, MCP и taste-skill

Файлы этого репозитория копируются в проект вместе с шаблоном. Внешние skills, MCP-серверы, браузерные инструменты и API-ключи **не устанавливаются автоматически**.

При старте проекта, смене стека или появлении нового непроверенного инструмента агент запускает capability gate:

- нужный инструмент есть — фиксирует и использует;
- обязательного инструмента нет — останавливается и предлагает установить его, продолжить в упрощённом режиме или остановить задачу;
- дополнительного инструмента нет — продолжает, честно записывая ограничение.

Встроенная anti-slop защита работает всегда: Design Read, дизайн-система, UX-ревью, реальные доказательства вместо фальшивых метрик и шаблонных блоков. Paper-эстетика запрещена, пока пользователь не отменит запрет прямо. [`taste-skill`](https://github.com/Leonxlnx/taste-skill) — рекомендуемый независимый визуальный критик для важных лендингов и первых экранов; его отсутствие не останавливает сборку, но фиксируется как ограничение ревью.

shadcn MCP помогает находить доступные примитивы интерфейса. Magic UI, Aceternity, React Bits и Motion — не обязательный «пакет красоты»: агент выбирает их только для конкретного компонента после visual gate и в рамках effect budget.

## Рабочий браузер для агента

Для реальной проверки сайт использует официальный Playwright CLI, а не полагается на случайно доступный browser MCP. Он работает из терминала и для Codex, и для Claude Code; MCP остаётся только fallback-путём. Один раз на компьютере установи CLI и его Chromium:

```bash
npm install -g @playwright/cli@latest
playwright-cli install-browser chromium
```

В Claude Code дополнительно можно один раз в папке конкретного проекта выполнить `playwright-cli install --skills` — это поставит справку по командам для Claude. Codex использует CLI по правилам шаблона и без этого шага.

В проекте агент запускает `scripts/browser-qa.sh <url>`. Скрипт сохраняет desktop/mobile-скриншоты и console errors, а подробный вывод CLI оставляет в файле вместо чата. При сбое агент делает один fallback, фиксирует `blocked` и не повторяет дорогую диагностику до изменения среды или явной команды пользователя.

## Visual gate

Для нового сайта, редизайна или новой визуальной системы агент обязан:

1. Зафиксировать Design Read, референсы, желаемое впечатление и запрет на paper.
2. Выбрать направление и собрать только первый экран с одной показательной сценой.
3. Проверить реальный результат на desktop и mobile, сохранить скриншоты и выводы в `docs/reviews/`.
4. Провести UX/anti-slop review, а при наличии — taste-pass.
5. Получить короткое решение «одобрить / переделать» до сборки остальных страниц.

Полная творческая свобода позволяет агенту выбрать направление, но не отменяет этот checkpoint. Если первый браузерный инструмент не сработал, агент обязан зафиксировать ошибку, попробовать доступный альтернативный путь и запросить решение: подключить браузер, разрешить настройку, прислать скриншоты или продолжить только как черновик. Ревью исходников не считается заменой реальной проверки.

## Что проверять после пилота

После первого реального проекта посмотри:

- [`workflow-log.md`](templates/project/workflow-log.md): какие workflow, skills и проверки реально принесли пользу;
- [`VERIFICATION.md`](templates/project/VERIFICATION.md): какие проверки агент смог выполнять автоматически;
- [`PROJECT.md`](templates/project/PROJECT.md): не слишком ли много модулей было включено;
- число кругов «переделай», качество первого экрана, проблемы на мобильном и ошибки перед релизом.

По этим фактам убирай лишнее и добавляй только то, что повторяется в твоих реальных проектах.

## Важные ограничения

- Это не готовый Next.js/Payload-стартер: пресеты описывают выбор стека, но не генерируют код сами.
- Роли — это последовательные точки проверки, а не автоматически запущенная команда независимых агентов.
- Шаблон улучшает качество решений и снижает количество переделок; он не заменяет продуктовый бриф, контент, реальные референсы и визуальную проверку.

## Структура

```text
SKILL.md                 # правила для установленного Codex skill
scripts/new-project.sh   # создаёт отдельную папку проекта
templates/project/
  AGENTS.md              # общие правила для агента в проекте
  CLAUDE.md              # точка входа для Claude Code
  PROJECT.md             # память о проекте, которую ведёт агент
  CAPABILITIES.md        # доступные skills, MCP и инструменты
  VERIFICATION.md        # реальные команды и проверки
  workflow-log.md        # фактический след работы и пилота
  docs/reviews/          # скриншоты и доказательства visual review
  profiles/              # website, CMS, security, mini apps и другое
  stack-presets/         # согласованные варианты стека
  scripts/browser-qa.sh  # реальная browser QA через Playwright CLI
  workflows/             # сценарии работы
    browser-qa.md         # обязательный протокол реальной проверки в браузере
```
